# 新任务从澪开始

用户可以先向澪说明研究问题、已有材料、项目位置、希望得到的结果和预算。不要求用户手写执行提示词。澪区分日常讨论和实际执行，读取源项目的规则索引、当前目标、状态与交接，只在已有授权范围内整理任务。缺少会改变科学问题或预算的信息时才向用户核实。

## 真实分工

1. 澪冻结任务问题、对象、输入、版本、允许动作、判据、预算与停止条件。
2. 琥珀对接真实 ChatGPT：提供用户已允许送往 ChatGPT 的必要上下文，选择适当强度，取得方案、竞争解释和分别给 Codex、Cursor、Grok 的优化提示词。私有论文、凭证、旧聊天不因“建立团队”自动获得上传授权。网页无法访问本机路径，必须提供已获准的内容或摘要，保留实际发送的完整提示词。
3. 本地校验把方案与冻结任务、网页会话、观察到的模型/强度、原始回答绑定。新增权限或改题不会靠模型输出获得批准。
4. 澪通过通用入口调用真实 Codex / Cursor。原生 Grok 探索交给明确的角色，生成待审候选；本地 outbox 不冒充已经调用了 Grok。
5. 原始结果、工具事件、会话、产物与摘要保存后，紫苑按具名风险审查，澪作最终接受决定。交付通过、数学结论、数值核查、适用性与创新度分别报告。
6. 只有对应版本与产物获得接受，依赖其成立的任务才继续。审核失败保留负结果，修订继承剩余预算；不会因换角色或重开聊天重置计次。

## 入口与边界

从团队根目录运行 `runtime/dispatch.py --help` 查看命令。典型顺序为 `create` → `request-plan`（仅新能力绑定或原请求阻塞时）→ `submit-plan` → `run` → 审查与回收。`status` 为本地只读状态；`cancel` 请求终止本任务拥有的执行。相同任务、版本和作业重读已有回执，不自动重新生成。

审查时先用 `review-scope --task ID --revision N --job JOB` 取得当前产物绑定；如要放行直接依赖，可加 `--approve-successor NEXT`。紫苑的指定范围判断和澪的接受决定分别保存为真实原生观察，之后运行 `record-review --task ID --revision N --job JOB --observation REVIEW.json`。具体字段见 `dispatch.py` 顶部协议与 `--help`。自审、错版本、变化产物或只有模板均不能放行；记录审核本身不自动生成后继，也不自动声明科学通过。

任务保存于 `runs/tasks/<task_id>/r<revision>/`。每项工程作业使用自己的输出子目录，源工程与历史结果保留。任务预算为绝对截止时间、作业数和修订上限，改版本不自动增加预算。未知发送状态先核原会话，回传失败仅重传原结果。

Cursor 仅对已校验 grant 绑定、位于本团队该任务隔离输出区的工程 workspace 自动确认工作区信任，并记录精确路径；原生沙箱保持开启。该确认不覆盖源科研仓库、整个用户目录或其他作业，也不启用 force/yolo/MCP 批量批准。外部仓库若遇信任要求，保留具体阻塞再处理。

当前通用入口支持 `read/derive/source_check/write_code/run_checks`。它不自动准入训练、模型评估、仿真、test 解封、收费接口或科研合同变更；这些动作需要源项目对应的具名授权和准入。读取指纹与散列不等于完成科学语义审查。

## ChatGPT 强度

复杂度依据理论未知、耦合子问题、已有失败与科学风险，常规采用 Medium，之后依次 High、Extra High、最高 GPT-6 Pro（6pro）。模型与强度分别记录。不同语言、浏览器或账户的标签必须在实际使用的界面重新核对；看到菜单不等于生成成功或有剩余额度。未登录、档位未知、限额或会话断开时保留任务，不偷偷换成 Grok、Codex 或付费 API。

真实来源可为本机 CUA、原生琥珀云浏览器，或用户明确取得的 ChatGPT 导出；三者按实际方式记录。自动回收与人工桥接分开。散列只绑定采集文件，依赖采集者如实记录，不是厂商签名或科学正确性证明。

一次公开任务成功只能证明该范围内链路可用。真实科研仍要逐项目继承输入、环境、预算、负结果和已完成工作，不因接入新工具重跑旧实验。
